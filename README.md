# Vacation Management

A web app for managing vacation requests, with two roles:

- **Requester** – submits vacation requests, follows their status (Pending, Approved, Rejected) and sees the team vacation plan.
- **Validator** – sees everyone's requests with filters and pagination, approves them, or rejects them with a required comment.

Built as a home assignment.

## Tech stack

| Part | Technology |
| --- | --- |
| Frontend | Vue 3, Vue Router, Axios, Tailwind CSS 4, Vite, TypeScript |

## Quick start

**Prerequisites:** Node.js 22 or newer (developed on Node 24), npm, and Docker (for PostgreSQL).

Open three terminals in the project folder.

**1. Database**

```bash
docker compose up -d
```

This starts PostgreSQL 16 in a container named `vacation-db` on port 5432 (user, password and database are all `vacation`). If you already have something on port 5432, stop it first.

**2. Backend** (port 8888)

```bash
cd backend
cp .env.example .env        # PowerShell or cmd: copy .env.example .env
npm install
npm run seed                # creates the tables, the demo users and a few sample requests
npm run dev
```

**3. Frontend** (port 5173)

```bash
cd frontend
npm install
npm run dev
```

Open <http://localhost:5173> and sign in with a demo account.

## Database setup

- `docker-compose.yml` starts the database. Data is kept in the `vacation_pgdata` volume.
- Tables are created and updated automatically from the TypeORM entities (`synchronize: true`), the first time the backend or the seed script connects.
- `npm run seed` is safe to run again: it only adds the demo users and sample requests when they are missing.
- To start again from an empty database: `docker compose down -v`, then `docker compose up -d` and `npm run seed`.

Schema:

- `users` – id, name, email (unique), password (bcrypt hash, never returned by queries), role (`Requester` or `Validator`), created_at.
- `vacation_requests` – id, user_id (foreign key), start_date, end_date, reason, status (`Pending`, `Approved`, `Rejected`), comments (the validator's rejection comment), created_at, updated_at.

## API

All routes except login need the header `Authorization: Bearer <token>`. Lists answer `{ items, total, page, limit }` and accept `?page=1&limit=10` (limit at most 50), newest first. Errors answer `{ "error": "message" }`.

| Method and path | Who | What | Errors |
| --- | --- | --- | --- |
| `POST /auth/login` | anyone | `{ email, password }` returns `{ token, user }` | 400, 401 |
| `GET /auth/me` | logged in | the user from the token | 401 |
| `POST /vacation-requests` | Requester | `{ startDate, endDate, reason? }` creates a Pending request (201) | 400, 401, 403, 409 |
| `GET /vacation-requests/mine` | Requester | own requests, paginated | 400, 401, 403 |
| `GET /vacation-requests` | Validator | all requests with the requester; filters `status`, `userId` | 400, 401, 403 |
| `PATCH /vacation-requests/:id/approve` | Validator | approves a Pending request | 400, 401, 403, 404, 409 |
| `PATCH /vacation-requests/:id/reject` | Validator | `{ comment }` rejects a Pending request | 400, 401, 403, 404, 409 |
| `GET /team/vacations` | any logged-in user | approved vacations (name and dates only), soonest first | 400, 401 |

Status codes: 400 invalid input, 401 not logged in or bad token, 403 logged in but wrong role, 404 not found, 409 the request clashes with the current data (overlap, or the request was already decided).

## Business rules and where they are enforced

The backend is the source of truth. The Vue forms and route guards only improve the user experience, because a client can always be bypassed.

| Rule | Where | Result |
| --- | --- | --- |
| End date is not before the start date (a one-day vacation is allowed) | create command handler | 400 |
| A vacation cannot start in the past | create command handler | 400 |
| No overlap with the same user's other requests (Rejected ones are ignored) | create command handler, database query | 409 |
| Only a Pending request can be approved or rejected; decided requests cannot be modified | approve and reject command handlers | 409 |
| Rejecting needs a non-empty comment | reject command handler | 400 |
| Only Validators approve or reject, only Requesters create | input parser, role check on the signed token | 403 |

## Architecture

### Request flow

```
Vue page
  -> Axios (JWT in the Authorization header, calls /api/...)
  -> Vite proxy (development) -> CEF server
  -> route in root.yaml
  -> input parser     checks the token, the role and the shape of the input
  -> API handler      thin: builds a command and dispatches it
  -> command bus      finds the one handler for that command
  -> command handler  business rules, TypeORM save, then publishes an event
  -> event bus        calls every listener subscribed to that event
```

An input parser that throws stops the request before the handler runs. Rule failures are thrown as typed errors (`BadRequestError`, `ForbiddenError`, `ConflictError`, ...) and `src/index.ts` turns them into the matching HTTP status.

### Commands and events

- A **command** is a request to do something that has not happened yet, so it can be refused. Each command has exactly one handler: `CreateVacationRequestCommand`, `ApproveVacationRequestCommand`, `RejectVacationRequestCommand`.
- An **event** is a fact that already happened, published after the command succeeded. An event can have many listeners: `VacationRequestCreatedEvent`, `VacationRequestApprovedEvent`, `VacationRequestRejectedEvent`.
- `CommandBus` and `EventBus` are small plain classes (`backend/src/shared/bus`), shared as one instance each. Handlers and listeners are registered once at startup in `backend/src/bootstrap.ts`.
- Reads (list my requests, dashboard, team plan) change nothing, so they are plain query functions without a command.
- A listener that fails is logged and does not fail the request, because the data is already saved.
- One listener is registered: `backend/src/listeners/audit-log.listener.ts` writes an audit line to the console for every created, approved or rejected request (failed commands publish nothing, so they leave no line). Adding another reaction, such as an email, is a new small listener and one line in `bootstrap.ts`. The business rules do not change.

### Project structure

```
backend/src
  index.ts                   CEF entry point and error mapping
  root.yaml                  routes (OpenAPI), each with x-handler and x-inputParser
  bootstrap.ts               registers command handlers and event listeners
  listeners/                 event listeners (audit log)
  modules/
    auth/                    login, current user
    users/                   User entity

```

## Technical decisions

- **CEF with parser and handler split.** The parser checks the token, role and input shape and fails fast. The handler never sees an unverified request. CEF calls parsers synchronously, so they cannot query the database. That is one more reason the database-dependent rules (overlap) live in the command handler.
- **Command and event layer.** For an app this small, plain function calls would also work. The layer keeps all rules in one place per action, keeps API handlers thin, and follows the open/closed principle: new reactions to an event are added without touching the rules.
- **Safe status changes.** Approve and reject update the row only if it is still Pending (`UPDATE ... WHERE id = ? AND status = 'Pending'`). Two validators clicking at the same moment get one success and one 409, instead of overwriting each other.
- **Stable pagination.** Every list has a fixed order with the id as tie-breaker, so pages never repeat or skip rows.
- **Password hash is never selected by default** (`select: false`). Only the login query asks for it. Login answers the same message for an unknown email and a wrong password.
- **The team plan returns only name and dates.** The reason is left out in the backend query, not hidden in the table, so it never reaches the browser.
- **Ids are limited to 32-bit integers** in the parsers, so a huge id gives a 400 instead of a database error.
- **Vite dev proxy.** The browser calls `/api` on the Vite port and Vite forwards to the backend. The CEF dev server's CORS answer does not allow `PATCH` from another origin.
- **Frontend state.** The server is the source of truth: after a create, approve or reject the lists are reloaded instead of patched locally. `usePagedList` ignores answers that arrive late, and moves back a page if the current page no longer exists.

## Known limitations

- **Events are in memory.** If a listener fails or the process stops, nothing retries. For production, events could be published to a queue (for example SQS or SNS), so listeners run separately and failures can be retried.
- **`synchronize: true`** creates the tables from the entities. Convenient for this exercise; a real system would use migrations.
- **JWTs cannot be revoked** before they expire (8 hours). The secret comes from `.env`; the committed value is for development only.
- **The token is kept in `localStorage`**, so a script injected into the page could read it. An HttpOnly cookie would be safer.
- **The Vite proxy is for development.** In production the frontend and the API should share an origin, or the server needs a proper CORS setup.
- **No automated test suite is included.** During development I checked the endpoints and the screens with scripted calls and browser runs, but those scripts are not part of the repository. The command handlers are written so they can be unit tested with a fake repository.
- **No deadline-based features**, no cancelling of a Pending request, no working-days count, no calendar view of the team plan, and the team plan lists all approved vacations including past ones.
- The Validator's user filter works by clicking a requester's name. A dropdown would need an endpoint that lists users.
